Chapter 1: Introduction

Practice Exercises

As we discuss in Section 1.1, the operating system serves three main purposes:

  • To provide an environment for a user to execute programs on the computer hardware in a convenient and efficient manner.
  • To allocate the resources of the computer (such as CPU time, memory, and I/O devices) as needed to solve problems. This allocation should be as fair and efficient as possible.
  • To act as a control program. This involves supervising the execution of user programs to prevent errors and improper use, and managing the operation and control of I/O devices.

This is an excellent question that gets at the different goals of an OS. In a single-user system, such as a personal computer (PC), it is appropriate for the OS to "waste" resources.

As we state in Section 1.1.1, the goal of a PC operating system is to **maximize the work (or play) that the user is performing.** It is designed for ease of use and user performance, not for resource utilization.

For example, a PC's CPU may sit idle for long periods waiting for the user to type on the keyboard. From a mainframe's perspective, this is a terrible waste. But for a PC, this "waste" is necessary to provide a fast, responsive experience when the user *does* provide input.

It is not "really wasteful" because the system is successfully meeting its design goal, which in this case is user convenience, not resource maximization.

As we discuss in Section 1.11.8, the main difficulty is that a real-time system has **rigid, fixed time constraints.**

Unlike a general-purpose system, where it is *desirable* to be fast, a real-time system *must* complete a task within a defined deadline. If the system fails to meet this deadline—even if the computation is logically correct—the system has failed. Therefore, the programmer must write the OS to guarantee that scheduling and I/O operations are performed within those constraints.

This is a fascinating debate, as we allude to in Section 1.1.3 ("Defining Operating Systems"). There is no universally accepted definition.

  • Argument that it SHOULD: An operating system's goal is to provide a "usable computing system." For most users, a computer is *unusable* without a web browser or email client. These applications are fundamental to the user's experience. As we see in mobile operating systems, including middleware for common services (graphics, databases, multimedia) is standard. Including a browser is a logical extension of this "user view" of the OS.
  • Argument that it SHOULD NOT: The "kernel" is the one program running at all times. Everything else is a system or application program. Including applications like browsers bloats the kernel, harms modularity, and makes the system less stable. It can also be anti-competitive, as the 1998 United States v. Microsoft case demonstrated. The OS should provide the *mechanisms* for applications to run, but not the applications themselves.

This is the most fundamental protection mechanism, which we cover in Section 1.5.1.

The hardware provides a **mode bit** to distinguish between user mode (1) and kernel mode (0). When a user application is running, the system is in user mode. When the OS gains control (via an interrupt or trap), it switches to kernel mode.

The hardware designates certain machine instructions as **privileged**. These are instructions that may cause harm, such as managing I/O, changing memory allocation, or modifying the timer. These privileged instructions can *only* be executed in kernel mode.

This provides protection by preventing a user program from, for example, directly accessing the disk or disabling the timer to hog the CPU. If a user program attempts to execute a privileged instruction, the hardware traps to the OS, which will terminate the errant program.

Based on the principle of protecting the OS and other processes (Section 1.5.1):

  • a. Set value of timer: Privileged. A user must not be able to change the timer, or they could prevent the OS from ever regaining control.
  • b. Read the clock: Not Privileged. Reading the time is a harmless operation.
  • c. Clear memory: Privileged. A user program must not be able to clear memory belonging to other processes or the kernel.
  • d. Issue a trap instruction: Not Privileged. This is the mechanism for a system call. It is the *only* way for a user to request a service from the kernel.
  • e. Turn off interrupts: Privileged. If a user program could turn off interrupts, it could prevent the OS from regaining control, effectively halting the system.
  • f. Modify entries in device-status table: Privileged. This is part of I/O management and must be protected.
  • g. Switch from user to kernel mode: Privileged. A user program cannot *arbitrarily* change the mode bit. It can only execute a trap, which *causes the hardware* to switch to kernel mode. An explicit "set mode bit" instruction is privileged.
  • h. Access I/O device: Privileged. All I/O control must be managed by the kernel to ensure protection and prevent conflicts.

This is an interesting historical approach. Two major difficulties would be:

  1. Updating and Patching: If the OS is in a read-only partition, it becomes impossible to apply security patches or bug fixes. The OS could never be updated without a hardware-level change, which is impractical.
  2. Dynamic Data: The OS is not static; it must maintain dynamic data, such as the list of current processes (the PCB list), I/O request queues, and interrupt vectors. If the OS partition is read-only, it cannot store this data internally. This data would have to be kept in a separate, modifiable RAM partition, which would then be vulnerable to errant user programs.

As we mention in Section 1.5.1, we can extend the mode concept. Two possible uses are:

  1. Virtualization: A **Virtual Machine Manager (VMM)** needs more privileges than a user process (it needs to manage virtual machines), but fewer privileges than the kernel. CPUs that support virtualization often have a separate mode for the VMM.
  2. Layered Protection: CPU designers, like Intel, provide multiple "privilege levels" (e.g., four rings). This allows for a more granular separation, such as placing the core kernel in the most privileged ring, device drivers in a slightly less privileged ring, and user applications in the least privileged ring.

This is a direct application of the timer interrupt we discuss in Section 1.5.2.

The operating system could maintain a global counter variable that stores the number of timer interrupts that have occurred since the system booted.

  1. At boot time, the OS would record a "start time" (from a hardware clock) and initialize a counter to zero.
  2. The hardware timer would be set to interrupt at a fixed, known rate (e.g., 1,000 times per second, or 1ms).
  3. In the timer's interrupt service routine, the OS would increment this counter.
  4. To compute the "current time," the OS would simply add the counter value (e.g., 55,000 ticks = 55 seconds) to the stored "start time."

We discuss caching as a core principle in Section 1.8.3.

Reasons Caches are Useful: 1. They bridge the speed gap between fast components (like the CPU) and slower components (like main memory), preventing the CPU from "stalling" while waiting for data. 2. They reduce the traffic on the main system bus, as the CPU can fetch data from its local cache instead of main memory.

Problem Solved: They solve the performance bottleneck of waiting for slower-speed storage.

Problem Caused: The primary problem is **cache coherency**, especially in multiprocessor systems (Section 1.8.3). If two CPUs have their own local caches, they can hold different (stale) copies of the same data, leading to inconsistency.

Why not make it that large? The simple answer is **cost**. The storage hierarchy (Section 1.2.2) is a trade-off between speed, cost, and size. Cache (e.g., SRAM) is significantly more expensive per bit than the device it caches (e.g., DRAM or disk). It would be prohibitively expensive to build a cache as large as a multi-terabyte disk.

We define these two models in our discussion of Computing Environments (Sections 1.11.4 and 1.11.5).

  • Client-Server Model: This is a centralized model. A central **server** process provides resources or services (e.g., a file server or web server). Multiple **client** processes request those services. The server is a bottleneck and a single point of failure.
  • Peer-to-Peer (P2P) Model: This is a decentralized model. All nodes in the system are **peers** and can act as *both* a client and a server. It is more scalable (every new peer adds capacity) and reliable (no single point of failure).

Exercises

This is a fundamental issue we address with protection mechanisms.

a. What are two such problems?

  1. Unauthorized Access (Confidentiality): One process reading the memory or files of another user or the operating system itself (e.g., reading a password file).
  2. Unauthorized Modification (Integrity): One process writing to and corrupting the data or code of another process, or even the kernel. This could crash the system or allow a malicious program to take control.

b. Can we ensure the same degree of security in a time-shared machine as in a dedicated machine? Explain your answer.

No. A dedicated machine (one user) is primarily secured by *physical* access. If you are the only one with a key to the room, your data is secure from other users.

A time-shared machine, however, relies on *software* (the OS) and *hardware* (the mode bit) to enforce logical separation. This logical protection is far more complex than physical protection. As we see in Section 1.5.1, any bug in the OS kernel could potentially lead to a protection failure. This complexity makes it inherently less secure than the simplicity of a dedicated machine.

As we discuss in Section 1.1, the goals of the OS change based on the environment.

  • a. Mainframe or minicomputer systems: The OS is designed to **maximize resource utilization.** All resources must be managed carefully: **CPU time, memory, file-storage space, and I/O devices.** The goal is to keep all users happy and the expensive hardware busy.
  • b. Workstations connected to servers: The workstation itself prioritizes user responsiveness, so its local resources are less of a concern. The critical resources to manage are **network bandwidth** and access to the shared **server resources** (like file storage or print servers).
  • c. Mobile computers: The primary constraints are **battery power** and **memory**. The OS must be aggressive in managing power to ensure usability, and it must manage the limited memory and smaller storage space efficiently.

A user would be better off with a time-sharing system in several circumstances (Sections 1.1, 1.4):

  • When the user needs to run a very large computation (a "big job") that requires more CPU power or memory than a standard PC provides.
  • When the user needs to access a massive, centralized dataset (like a large database) that cannot be stored on a single PC.
  • When cost is a primary factor and it is cheaper to provide one powerful time-shared system and many "dumb terminals" than to buy hundreds of full-featured PCs.
  • When active collaboration is required, such as in a transaction system where many users must access the same data concurrently.

We discuss this in Section 1.3.2, "Multiprocessor Systems."

Differences: In **asymmetric multiprocessing (AMP)**, there is a "boss-worker" (or master-slave) relationship. One processor (the boss) controls the system and schedules work for the other processors. In **symmetric multiprocessing (SMP)**, all processors are peers. Each processor runs all tasks within the OS, including scheduling itself. This is the most common modern approach.

Three Advantages:

  1. Increased Throughput: We get more work done in less time.
  2. Economy of Scale: It is cheaper to have one system with multiple processors than multiple separate computers, as they can share peripherals, storage, and power supplies.
  3. Increased Reliability: If one processor fails, the system does not halt; it just slows down. This is called **graceful degradation**.

One Disadvantage: Increased complexity in both the hardware (e.g., ensuring cache coherency) and the software (e.g., writing an OS that can run on multiple processors at once without race conditions).

We make this distinction in Section 1.3.3.

Difference: Multiprocessor systems are **tightly coupled**; they are a *single computer* sharing memory, a bus, and a clock. Clustered systems are **loosely coupled**; they are *multiple, independent computers* (or nodes) that are joined together by a network (like a LAN).

Requirements for High Availability: For two machines to cooperate in a high-availability cluster, they require:

  1. Shared Storage:** A network (like a SAN) that allows both nodes to access the same data.
  2. Monitoring:** Cluster software that runs on each node to monitor the others (often a "heartbeat" over the network) so that a failure can be detected.
  3. Locking:** A **Distributed Lock Manager (DLM)** is required to ensure that the nodes do not access the shared storage at the same time and corrupt the data.

We discuss these two clustering models in Section 1.3.3.

1. Asymmetric Clustering (Hot-Standby): One machine is the active server, running the database and handling all requests. The other machine is in "hot-standby" mode, doing nothing but monitoring the active server. If the active server fails, the standby machine takes over.

  • Benefit: It is simple to implement, as there are no data-access conflicts to manage.
  • Disadvantage: It is inefficient. Half of the hardware resources (the standby node) are sitting idle and not being used.

2. Symmetric Clustering: Both hosts are running the database application and monitoring each other. Both can handle requests concurrently.

  • Benefit: It is highly efficient and provides high performance, as all hardware is being used.
  • Disadvantage: It is very complex to implement. It requires a distributed lock manager (DLM) to ensure that the two nodes do not try to write to the same piece of data at the same time.

We discuss this in Section 1.11.1, "Traditional Computing."

Difference: A traditional PC is a "fat client"—a complete system with its own OS, storage, and processing power. A **network computer** (or **thin client**) is a simple terminal that relies on a central server for all of its storage, processing, and applications. It is essentially just a screen and keyboard.

Advantageous Scenarios:

  • Centralized Administration: In a large company, it is easier to update an application *once* on the server than to update it on 1,000 separate PCs.
  • High Security: Useful in banks or military settings. Since there is no local storage (no hard drive), users cannot install unauthorized software or steal sensitive data.
  • Lower Cost: Thin clients are much cheaper to purchase than full-featured PCs.

We cover this in Sections 1.2.1 and 1.5.1.

Purpose of Interrupts: The purpose of an interrupt is to signal the CPU that an event has occurred, which causes the CPU to stop its current task and transfer execution to the operating system (the interrupt service routine). This allows I/O devices to run concurrently with the CPU, interrupting only when they are finished.

Interrupt vs. Trap: An **interrupt** is *asynchronous*. It is generated by **hardware** (like a timer, a disk controller, or a keyboard) at any time, unrelated to the instruction the CPU is currently executing. A **trap** (or exception) is *synchronous*. It is generated by **software** as a direct result of executing an instruction. This can be caused by an error (like division by zero) or, as we see next, it can be intentional.

Can traps be generated intentionally? **Yes.** This is the fundamental mechanism for a **system call**. A user program intentionally executes a trap instruction to request that the operating system perform a privileged task on its behalf, such as reading a file or accessing a device.

We describe the DMA process in Section 1.2.3.

a. How does the CPU interface with the device to coordinate the transfer? The CPU "sets up" the transfer by writing several values into the registers of the **DMA controller**:

  1. The starting memory address for the data.
  2. The I/O device address.
  3. The number of bytes to transfer.
  4. The direction of the transfer (read from device or write to device).
Once set, the CPU is free to do other work.

b. How does the CPU know when the memory operations are complete? The DMA controller sends a single **hardware interrupt** to the CPU when the *entire block* of data has been transferred. This is far more efficient than the alternative, which would be one interrupt *per byte*.

c. The CPU is allowed to execute other programs while the DMA controller is transferring data. Does this process interfere with the execution of the user programs? If so, describe what forms of interference are caused. **Yes, it does interfere**, though in a minor way. Both the CPU and the DMA controller need to access the memory bus to read or write data. Since only one can use the bus at a time, the DMA controller must "steal" memory cycles from the CPU. This forces the CPU to wait, which can slightly slow down the execution of the user program. This interference is known as **cycle stealing**.

This question challenges the core assumption of Section 1.5.1.

Argument: YES, it is possible. We could construct a secure OS if we do not run native code. If all programs are run through a software **interpreter** (like a JVM), the interpreter itself can check every instruction for safety before executing it, thus providing software-based protection. We could also use a **type-safe language** and a verifying compiler to achieve the same result.

Argument: NO, it is not possible. For a *general-purpose* operating system that runs arbitrary user-compiled (native) programs, it is impossible. Without a privileged mode, a user program could simply:

  • Write directly over the operating system's memory.
  • Disable interrupts and never return control to the OS.
  • Directly access any I/O device.
There would be no way for the hardware to enforce any protection, so the system would be completely insecure.

This is a hardware design trade-off, as we discuss with SMP architectures in Section 1.3.2 and caching in Section 1.8.3.

  • Local Cache (L1/L2): This cache is private to the core and provides the *fastest* possible access to data. Its purpose is to keep that specific core full of instructions and data, minimizing latency and reducing traffic on the main system bus.
  • Shared Cache (L3): This cache is shared by *all* cores. Its purpose is to provide a fast way for cores to **share data** with each other. It is much faster than communicating via main memory, and it helps mitigate the **cache coherency** problem, as all cores have a common view of this data.

This illustrates the **cache coherency** problem (Section 1.8.3):

  1. Assume a variable `X` in main memory has the value `5`.
  2. CPU 0 reads `X`. A copy of `X` with value `5` is placed in CPU 0's local cache.
  3. CPU 1 reads `X`. A copy of `X` with value `5` is placed in CPU 1's local cache.
  4. CPU 0 writes `X = 10`. It updates *only its local cache* to `10`.
  5. Result: The system is now in an incoherent state. Main memory has `X=5`, CPU 1's cache has `X=5`, and CPU 0's cache has `X=10`. If CPU 1 accesses `X` again, it will read the stale value of `5`.

We discuss this in Section 1.8.3. The problem is about ensuring all copies of data are up-to-date.

a. Single-processor systems: The problem is between the **CPU cache** and **I/O devices** using DMA. * **Example:** The CPU updates a variable `A` in its cache. It then tells the DMA controller to write `A` to disk. The DMA controller reads from main memory, which still has the *old* value of `A`. The OS must explicitly **flush** the cache to memory before initiating a DMA write to ensure the I/O device gets the correct, new data.

b. Multiprocessor systems: The problem is between the **local caches of different CPUs**. * **Example:** As in 1.23, CPU 0 updates `A` in its cache, and CPU 1 has a stale copy of `A` in its cache. This is typically solved by hardware (e.g., bus snooping) where a write to one cache *invalidates* the copies in all other caches.

c. Distributed systems: This is not a hardware cache problem, but a *software* caching problem. * **Example:** A **distributed file system**. Node A in the cluster downloads (caches) a file from the server. Node B downloads the same file. Node A modifies the file and saves it back to the server. Node B's local copy is now stale, and it is unaware of the change. This must be solved by software, such as a distributed lock manager.

As we describe in Section 1.5.3, the most common hardware mechanism is the use of a **Base Register** and a **Limit Register**.

These two registers define the legal address space of a process:

  • The **Base Register** holds the smallest legal *physical* memory address.
  • The **Limit Register** specifies the *size* of the legal range.

For every memory access a user program makes, the CPU hardware automatically checks if the address is between `base` and `base + limit`. If the address is outside this range, the hardware generates a **trap** to the operating system, which will terminate the program for illegal memory access (a segmentation fault).

We define these network types in Section 1.11.3.

  • a. A campus student union: LAN (Local-Area Network). A LAN connects computers within a single building or campus.
  • b. Several campus locations across a statewide university system: WAN (Wide-Area Network). A WAN links systems across geographically separate areas like cities or countries.
  • c. A neighborhood: LAN. While larger than a single building, it is still a small, contained geographic area. A very large metropolitan network might be a MAN, but LAN is the better fit of the two choices.

We discuss the mobile computing environment in Sections 1.1.1 and 1.11.2. The challenges are significant:

  1. Power Management: This is the most critical challenge. The OS must be extremely aggressive in managing the CPU, screen, and radios to conserve battery life, which is a very limited resource.
  2. Resource Scarcity: Mobile devices have less memory and typically slower processors than PCs. The OS itself must have a small memory footprint and manage application memory tightly.
  3. User Interface:** The OS must be designed for a touchscreen (handling gestures) and a small screen, which is a completely different paradigm from the mouse and keyboard of a PC.

As we compare in Sections 1.11.4 and 1.11.5, the peer-to-peer (P2P) model has key advantages:

  • Increased Reliability: In a client-server system, if the server fails, the entire service stops (a single point of failure). In P2P, the failure of one peer does not stop the network.
  • Increased Scalability: In a client-server system, the server is a bottleneck as more clients join. In a P2P system, every peer that joins *adds* new capacity (storage, bandwidth) to the network, allowing it to scale.

Based on the P2P model described in Section 1.11.5, appropriate applications are decentralized:

  • File-sharing networks like Gnutella or BitTorrent, where the data is distributed among all peers.
  • Voice over IP (VoIP) services like the original Skype, where the call data is routed directly between user (peers) rather than through a central server.
  • Distributed search and discovery systems where there is no central index, and peers must ask each other for information.

We discuss this in Section 1.12, "Open-Source Operating Systems."

Advantages:

  • For Students/Learners: The ability to study the source code is an invaluable learning tool.
  • For Everyone: A large community of programmers helps find and fix bugs, arguably making the code more secure and reliable ("many eyes").
  • For Users/Companies: The software is typically free of cost.

Disadvantages:

  • For Commercial Software Companies: They may not want to open-source their code and reveal their proprietary ideas to competitors.
  • For Content Producers: The open-source model is incompatible with Digital Rights Management (DRM), as the source code for the copy protection would be visible.
  • For some Corporate Users: May lack a single, guaranteed support channel, although companies like Red Hat have built a business model around providing this support.
